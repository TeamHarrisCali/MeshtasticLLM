# Meshtastic LLM Bridge

**Ask a local AI questions over a LoRa radio mesh. No internet, no cloud, no account.**

Meshtastic LLM Bridge connects a [Meshtastic](https://meshtastic.org) radio to a model running on your own computer through
[Ollama](https://ollama.com). Anyone on your mesh can send the radio a direct message such as `/ai which nodes have low batteries?`
and the answer comes back over the air as short messages; a local web dashboard shows what is happening on the mesh and controls
who may ask what. It is for people who run their own Meshtastic radios and want a private assistant for them. It is a hobby project.

## Requirements

- A Meshtastic radio, normally connected over USB (firmware 2.5 or newer for the encrypted-DM features). Bluetooth and Wi-Fi radios work too.
- [Ollama](https://ollama.com/download) with at least one model that supports tool calling (for example `qwen3.5` or `llama3.2:3b`).
- Python 3.9 or newer on Windows, Linux or macOS. Setup builds its own virtual environment.

## Quick start

The installer is the main way to run the bridge and supports everything: USB, Bluetooth, Wi-Fi and failover.

```bash
git clone https://github.com/TeamHarrisCali/MeshtasticLLM.git
cd MeshtasticLLM
./setup.sh                 # Linux / macOS     (Windows: double-click setup.bat)
./scripts/start_bridge.sh  # runs in the background; ./scripts/stop_bridge.sh stops it
```

Setup finds Python, builds `.venv`, installs the dependencies and checks Ollama and the radio. It is safe to run again, prints the exact
command for anything missing, and `./setup.sh --check` only reports. Then open <http://127.0.0.1:8080/> and, from another node, send your
radio a direct message such as `/ai help` or `/ai where is the nearest router?`. No flags are needed ([flags](docs/flags.md) are optional
overrides). On Windows start the bridge with `scripts\start_bridge.ps1`; see [docs/setup.md](docs/setup.md). No radio yet?
`.venv/bin/python -m meshllm --demo` runs everything against a simulated mesh ([demo mode](docs/setup.md#try-it-without-hardware-demo-mode)).

### Run with Docker (second option)

If you would rather not install Python or Ollama, `./setup.sh --docker` starts the bridge and its own Ollama in containers
(`--docker --demo` tries the dashboard first, with no radio). Docker does **not** do everything the installer does:

- **No Bluetooth.** A container cannot reach the host's Bluetooth, so a Bluetooth radio, `--ble-scan` and USB-with-Bluetooth failover need the installer.
- **USB only on Linux.** Docker Desktop on Windows and macOS cannot pass a USB serial device to a container; use a Wi-Fi radio there (`setup.bat --docker --tcp ADDRESS`).
- **No USB hot-plug.** After replugging the radio, run the setup command again.
- **Separate data.** Docker keeps its own database and its own copy of the AI model, apart from any bridge or Ollama you already run.
- **No log viewer.** The container writes no log files; use `docker compose logs -f bridge`.

Without a password the container's dashboard has no login, so Compose publishes it on this computer only; if you run the image without
Compose, publish with `-p 127.0.0.1:8080:8080`, never `-p 8080:8080`. Full steps, the login, backups and updating: [docs/setup.md](docs/setup.md#run-with-docker).

### Download a program (third option)

No Python and no Docker: a ready-made program for Linux, Windows and macOS, to unpack and run (`./meshllm --demo` is a quick try). Releases appear on the
[GitHub Releases page](https://github.com/TeamHarrisCali/MeshtasticLLM/releases) once the first one is published; **none exists yet**. The programs are unsigned
(Windows and macOS will warn) and not yet tried on a real radio; see [docs/releasing.md](docs/releasing.md).

## Status

What has been tried on real hardware (the automated tests fake the radio and Ollama; [docs/roadmap.md](docs/roadmap.md) lists the rest):

- USB and Bluetooth have been tested on one real radio (a Heltec V3), including USB-to-Bluetooth failover and recovery after a reboot.
- **Wi-Fi/TCP is not tested on real hardware**; it is covered only by automated tests with a simulated connection.
- Docker was built and tried on Linux with the demo and without a radio. **Docker Desktop is not tried.**

## Key features

- **Answers over the radio.** `/ai <question>` by direct message; replies are split into numbered parts that fit a LoRa packet, acknowledged and re-sent.
- **Knows your mesh.** The AI looks things up in what your radio has heard (nodes, batteries, sensors, signal, quiet nodes, history) and says "I can't tell" instead of inventing numbers.
- **Finds the radio by itself** and reconnects after an unplug, a swap or a reboot; USB, Bluetooth, Wi-Fi and failover between them.
- **A full dashboard:** map, nodes with your own labels, coverage, traceroute, telemetry, radio settings backup, diagnostics and an AI log; an evaluation harness scores how reliably a model picks the right tool.
- **Runs unattended:** background start and stop, start at login, daily backups. Everything stays on your computer; the only outbound connections are ones you ask for.

## Safety

A radio mesh is an open channel and any text on it can be hostile, so the AI is boxed in:

- It answers **direct messages only**, starting with `/ai`, and never reads the public channel; access control, a daily cap and a block list apply.
- Tools are **opt-in per node**: enabled by you, the node's public key pinned, and the message sent as a PKI-encrypted DM.
- The model can only pick from a **fixed menu of read-only lookups**. It has no shell, cannot touch your files and cannot transmit on its own.
- The dashboard listens on `127.0.0.1` with no login; on any other address it refuses to start without a password and a host allow-list.

The full table, and what this does not protect against, is in [docs/ai_tools.md](docs/ai_tools.md#the-safety-layers-at-a-glance). To report a vulnerability, see [SECURITY.md](.github/SECURITY.md).

## Tests

```bash
python scripts/run_tests.py                 # everything, a few minutes; no radio or Ollama needed (both are faked)
python scripts/run_tests.py channel backup  # only the test files whose names contain these words
```
The tests use a throwaway temporary folder, so your real `audit.db`, `tile_cache/` and `logs/` are never touched.

## How this is built

The code, tests and documentation are written by Anthropic's Claude models through Claude Code; a human maintainer sets the goals, owns
the repository and has authorised this workflow, including AI agents merging reviewed pull requests. Work follows a small team's habits (a
convention, not enforced by GitHub): one branch and one pull request per task, a separate reviewer agent that reads each pull request cold,
and a merge only when CI is green and the review is clean. The reviewer is the same model family as the author, so it is not a substitute
for a human reading the code. Human contributors go through the same flow.
